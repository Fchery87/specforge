1 Context and goals 3 clauses 7 claims Confirmed
A specification is read twice: once by a person deciding whether it is right, and once by an agent deciding what to build. This document is written for the first reader.
1.1 REQ-1.1 Confirmed 4 claims E-01E-02E-03 4/4
The specification is the product

SpecForge turns a product brief into a numbered specification that a coding agent can execute. The specification is the primary artifact, and a person reads it before an agent does. Every clause therefore carries a stable requirement ID, at least one claim, and a link to the evidence behind that claim.

  • REQ-1.1a

    A clause keeps its requirement ID when it is re-drafted, so a reference from another artifact still resolves.

  • REQ-1.1b

    A claim without evidence is visible as unlinked and blocks the stage gate.

1.2 REQ-1.2 Confirmed 2 claims E-04 3/3
Success is measured on the review surface

A lead reads a drafted PRD in one sitting, resolves every clause marked for review, and exports a handoff pack without editing markdown by hand. Review time is the metric, and the interface is built to shorten it.

1.3 REQ-1.3 Confirmed 1 claim E-04 2/2
Out of scope

The product does not write application code, does not run a review of committed code, and does not choose a model for the member. Those belong to the agent the member already uses.

2 Roles and permissions 2 clauses 5 claims Confirmed
Three roles. The server checks every mutation, and the client mirrors the check only to decide which controls render.
2.1 REQ-2.1 Confirmed 3 claims E-05E-06 5/5
Three workspace roles

A workspace has an owner, editors, and viewers. Editors do the work, owners change the membership, and viewers read. The table below is the whole policy, and every row is covered by a conformance check.

A permission change writes one audit event and takes effect on the next request. Cached permissions expire after 60 seconds.
2.2 REQ-2.2 Confirmed 2 claims E-07 4/4
The server is the only authority

Every mutation re-reads the role from the workspace record. A request forged from the client fails with a forbidden error and writes no data.

3 Projects and workspaces 4 clauses 8 claims Confirmed
A workspace holds projects. A project holds artifacts, runs, and evidence. Membership is workspace scoped.
3.1 REQ-3.1 Confirmed 2 claims E-05E-06 2/2
A project belongs to one workspace

A project is created inside a workspace and stays there. Moving a project between workspaces is not supported, and the interface does not offer it. Members of the workspace read every artifact in the project.

  • REQ-3.1a

    A project records workspaceId at creation and never rewrites it.

  • REQ-3.1b

    Listing projects reads the workspace index only, so a member never sees a project from another workspace.

3.2 REQ-3.2 Confirmed 1 claim E-07 3/3
Creating a project assigns the creator as owner

The member who creates a project becomes its owner. The project starts in the Draft state with the Brief phase pending, and the creator can hand ownership to another editor at any time.

3.3 REQ-3.3 Confirmed 2 claims E-08E-09 4/4
Deleting a workspace is a soft delete

Deleting a workspace hides it and its projects from every member for 30 days. During that window an owner can restore it, and the Evidence index keeps serving requests from restore flows. After 30 days the workspace and its artifacts are hard deleted.C-031Claim C-031

Restoring a workspace brings back every project with its evidence links intact.

4.1 REQ-4.1 Confirmed 2 claims E-11E-12 3/3
Create a project from a brief

An editor creates a project by answering the Brief questions. The project is created before the first generation run, so a failed run never loses the answers.

  • REQ-4.1a

    Answers save as they are typed, and a revision is written when the member leaves a question.

  • REQ-4.1b

    Starting a run with an unanswered required question fails validation before the provider is called.

4.2 REQ-4.2 Needs review 3 claims E-14E-15E-19 2/3
Archive a project

A workspace member with the editor role may archive a project. Archiving sets status = archived, keeps all artifacts readable, and writes one audit event. Archived projects do not accept new generation runs.

Archive is available from the project header and from the pipeline spine. The member who archives a project keeps the ability to restore it for 90 days.

  • REQ-4.2a

    Archiving writes one audit event with the actor, the project ID, and the previous state.

  • REQ-4.2b

    Artifacts stay readable while archived, including the evidence links on every claim.

  • REQ-4.2c

    A generation run created before the archive event finishes; a run created after it is rejected with a validation error.

5.4 REQ-5.4 Confirmed 3 claims E-30E-31 3/3
Living spec drift

When an upstream artifact changes, every clause that read it is marked Stale. A stale clause keeps its text and shows the change that caused it, so a reviewer can compare before re-drafting.

6 Evidence and claims 3 clauses 12 claims Confirmed
A claim is a sentence a reviewer can check. Evidence is where they check it.
6.1 REQ-6.1 Confirmed 5 claims E-33E-34 5/5
Every claim names its source

A claim links to at least one evidence item: an interview answer, a commit-pinned file, or a document the member attached. A claim with no evidence is visible as unlinked and blocks the stage gate.

6.2 REQ-6.2 Confirmed 4 claims E-35 4/4
Evidence is pinned, not paraphrased

A file reference records the commit and the line range. A later commit does not change the evidence; a reviewer sees the pinned revision and can compare it with the current one.

6.3 REQ-6.3 Confirmed 4 claims E-36E-37 3/3
Stress-test grilling is evidence too

An answer given during a stress-test session attaches to the clause it defends. The transcript is evidence, and the clause shows it the same way it shows a commit.
